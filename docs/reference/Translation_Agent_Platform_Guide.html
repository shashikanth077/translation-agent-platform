The big picture

1. The problem with a TMS-style application

A traditional translation management system (TMS) is a workflow application: project managers create projects, upload files, assign linguists, and tools such as translation memory (TM) and termbases help humans translate. For a life-sciences organisation with many clients, languages, document types and regulatory rules, running four separate legacy TMS products meant duplicated assets (TMs, glossaries), inconsistent quality, manual hand-offs, slow turnaround and high per-word cost. Hard-coded workflows and a UI-first design (a single React application driving fixed screens) made every new rule a code change.

DimensionLegacy TMS landscapeAgentic platform
WorkflowFixed, configured per system; humans move work between steps.Graph of agents/nodes; routing decided at run time from risk, QE scores, cost and policy.
IntakeForms and emails; PM interprets requests.Conversational agent produces a validated JobSpec; asks for what is missing.
Quality controlHuman review of most or all content, sampled LQA.Automated multi-metric scoring first; humans focus on the risky segments.
AssetsTM/termbase siloed per system.One canonical TM, termbase and cache serving every client and workflow.
CostPay for every word at similar effort.Reuse first, cheapest adequate engine next, expensive steps only when needed.
IntegrationCustom connectors, brittle.Services with contracts; capabilities exposed to agents as MCP tools.
ChangeVendor release cycles.Independent services; models and prompts swapped behind adapters, proven by A/B tests.

2. Design principles (say these in interviews)

  • Reuse before generate: cache and TM first; every avoided model call is free quality and free cost savings.
  • Cheapest adequate path: route by risk and measured quality, not by habit; escalate only when scores say so.
  • Never trust one judge: multiple evaluators plus deterministic checks (numbers, terms, tags); disagreement is a signal.
  • Deterministic where it matters: numbers, units, dosages, terminology and format are checked by code, not by a model's opinion.
  • Humans where risk is high: regulatory and patient-facing content gets risk-based human review; humans are in the loop by design, not as an afterthought.
  • Safe tools, not free access: agents call platform capabilities only through a gateway with schemas, scopes, approvals and audit.
  • Everything observable and evaluable: traces, datasets, metrics and A/B tests make improvements provable.
  • Strangle, don't big-bang: migrate the legacy systems gradually behind adapters and a canonical data model.

Multi-agent orchestration (the heart of the platform)

  
Instead of one application with fixed screens, the platform is a team of specialised agents coordinated by an orchestrator. This tab explains the patterns, when to use agents versus plain functions, how LangGraph implements them, the agent roster of a translation platform, and the failure modes you must control.


  
1. Agent versus workflow versus function

  

    
Building blockWho decides the next step?Use whenTranslation example

    
Function / serviceYour code, fixedLogic is deterministic and well definedSegmentation, number checks, cache lookup, COMET scoring

    
Workflow (graph with conditional edges)Your code, via explicit rules over stateSteps known, routing depends on dataIf QE below threshold go to repair, else accept

    
Agent (LLM chooses actions/tools)The model, within limits you setOpen-ended input, ambiguous goals, tool selectionConversational intake; terminology resolution; repair strategy

    
Multi-agent systemSupervisor or peers, with handoffsDistinct skills, tools or permissions per roleIntake, translator, evaluator, repair and delivery agents collaborating

  

  
Rule of thumb for interviewsUse the least autonomy that works. Put deterministic work in services, known routing in graph edges, and use LLM agents only where language understanding or open-ended decisions are genuinely needed. Fewer agent decisions means lower cost, lower latency and easier validation.

5. How state and communication work

  
    
    
  • Shared graph state (a typed object): job spec, segments, candidate translations, scores, decisions, cost counters, errors. Nodes read it and return partial updates; reducers define how updates merge (append to a list, overwrite a field).
    • 
    
  • Handoffs: a node returns the next destination (conditional edge or a command that updates state and routes). The receiving agent sees only the state it needs, which keeps prompts small.
    • 
    
  • Memory: short-term = checkpointed graph state per job (thread); long-term = TM, termbase, client style guides and past decisions in stores the agents query through tools.
    • 
    
  • Tools: each agent gets a minimal tool set via the MCP gateway (least privilege). The evaluator cannot publish; the delivery agent cannot translate.
    • 
    
  • Human in the loop: an interrupt pauses the graph, persists state, and resumes when a reviewer submits a decision.
    • 
  


  
6. Failure modes of multi-agent systems and the controls

  

    
Failure modeWhat it looks likeControl

    
Infinite or long loopsRepair agent and evaluator ping-pongMax iterations per segment, budget caps, escalate to human after N tries

    
Cost explosionLLM called for every segment, retries multiplyCache first, router thresholds, per-job budget, cost counters in state, alerts

    
Error propagationA wrong early decision poisons later stepsValidate state at each boundary with schemas; deterministic checks between agents

    
Conflicting agentsJudges disagreeExplicit consensus rule; disagreement triggers repair or human review

    
Context bloatWhole job history in every promptPass only needed state; summarise; segment-level subgraphs

    
Unsafe tool useAgent calls a write tool wrongly or after prompt injectionGateway with allow-lists, scopes, schema validation, approvals, audit; treat tool outputs as untrusted

    
Non-determinismSame input, different routeLow temperature, versioned prompts, seed where possible, record decisions in traces, regression datasets

    
Hard to debugWhich agent caused the bad output?LangSmith traces per node, run IDs, replay from checkpoints

    
Duplicate side effectsRetried step publishes twiceIdempotency keys, outbox pattern, publish only after approval node
